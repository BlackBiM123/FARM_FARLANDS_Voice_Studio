# Интеграция Voice Studio и существующей игры Godot

Дата: 19 октября 2026. Статус: анализ и проект контракта для согласования.
Игровой репозиторий: BlackBiM123/farm-and-farlands.
Исследованный commit: ddc03a4c4d50467d439773107e14b0847c8b9467 (HEAD основной ветки на момент чтения).
Код игры, база Studio и опубликованный сервис не изменялись. Проверка статическая: движок и игровые тесты не запускались. Локальная копия для анализа разреженная, без полного набора графических ресурсов.

## Подтверждённое состояние игры

- project.godot объявляет Godot 4.7, GL Compatibility; главная сцена scenes/region/region_main.tscn. Это версия формата/целевых возможностей проекта, а не проверенная версия установленного исполняемого файла.
- autoload: EventBus, DataRegistry, SaveGame, GameClock, Weather, AudioManager, AudioEvents.
- scenes/region/region_map.tscn сейчас объединяет S4 и S5 в одном дереве; S5 смещён на Vector2(3360, 0), общая граница открыта. Девять логических сцен нельзя трактовать как девять уже существующих независимо загружаемых уровней.
- scripts/region_map.gd объединяет габариты дочерних GameMap для камеры. GameMap задаёт bounds, не граф переходов и не симуляционное место.
- scripts/npc.gd — физический Npc с MovementComponent, AnimationComponent, WanderComponent. Wander выбирает случайные точки вокруг дома, ждёт и прекращает движение при застревании. Это локальная прогулка без жизненных целей, работы и межсценового путешествия. В прочитанном классе нет постоянного npc_id и интерфейса сохранения состояния NPC.
- GameClock — общие детерминированные часы на физических тиках. Реальная игровая минута по настройке равна 0,7 с. Сезон 28 дней. День начинается 06:00, предел бодрствования 02:00 следующей ночи. Есть advance_minutes, minute_passed/hour_passed, пауза, ускорение и сохранение day/minutes.
- GameClock.sleep сейчас сразу увеличивает day и выставляет 06:00, затем публикует day_changed. Пропущенные минуты не исполняются. Это нужно явно учитывать при добавлении ночной автономии, особенно с ранним сном игрока.
- SaveGame использует устойчивый save_id, save_state/load_state, JSON и версию схемы с точками миграции. collect_state/apply_state работают с группой узлов saveable в текущем дереве. Отсутствующий физический NPC не попадёт туда автоматически: состояние всех NPC должен сохранять постоянный владелец реестра, а не только акторы загруженной карты.
- EventBus намеренно содержит только сигналы; некоторые события передают Node. Для долговечного журнала нужна отдельная сущность, а сообщения журнала должны ссылаться на ID, не на узлы. Наличие сигнала trade_completed ещё не доказывает наличие рынка.
- DataRegistry загружает .tres/.res определения предметов, ресурсов, погоды, сезонов, культур, звуков. Проверяются ID, дубликаты и ссылки.
- ItemDefinition уже содержит id, unit_weight, base_value, max_stack, category, market_category и tags. Эти данные нельзя независимо завести заново в Studio без определения владельца каталога.
- InventoryComponent/StorageComponent и ItemTransfer уже обеспечивают игровое хранение и перенос предметов; ItemTransfer возвращает непринятый остаток источнику. Есть вес/нагрузка, энергия, почва, рост культур и сбор урожая. Это реальная основа производства, но ещё не автономная экономика предприятий.
- В исследованных scripts/autoload нет реализации Utility AI/HTN, денежного реестра счетов, собственности на жильё, автономных предприятий или импорта определений NPC из Studio.
- Есть headless-раннер tests/test_runner.tscn: тест подключается обычной сценой с autoload, а не godot --script. tests/run_all.sh импортирует ресурсы и запускает тесты по одному. Новую симуляцию следует проверять тем же способом.

## Как использовать существующее

| Система игры | Следующее расширение — предложение |
|---|---|
| GameClock | Единый абсолютный отсчёт и обработка пропущенных интервалов, сохраняя календарь и дневные события |
| SaveGame | Постоянный WorldSimulation как участник сохранения, включая всех удалённых NPC |
| DataRegistry + ItemDefinition | Чтение существующего каталога и проверка itemId; сначала импорт каталога в Studio только для справки |
| InventoryComponent + ItemTransfer | Общие правила количества, вместимости и веса; отделение состояния от визуального узла и адаптер для локального исполнения |
| Npc + Movement/Animation | Видимое представление NPC, связанное с постоянным npcId и одним состоянием путешествия |
| EventBus | Уведомления систем; отдельно EventJournal с ID, игровым временем и уникальными событиями |
| Карта S4/S5 | Первая проверка движения и переключения детализации в уже существующей геометрии |
| Сценарии Studio | Импорт определений; проверка исполняемой части в ядре Godot, сохранение объяснительного текста |

## Предлагаемый минимальный контракт

Не утверждён и пока не реализован.

1. Пакет content_manifest: schemaVersion, contentRevision, contentHash, engineCompatibility; список файлов и их контрольных сумм.
2. Определения: NPC с существующими ID Studio; регионы/секторы/места; рёбра маршрута; определения действий и целей; сюжетные ограничения; начальные условия. Не переименовывать старые NPC.id по новому имени.
3. Привязки Godot отдельно от условной карты: logicalSceneId/placeId, scene resource path (может отсутствовать), локальный anchor и преобразование координат. Отсутствие графической сцены не означает отсутствия места в мире.
4. Предметы в первом прототипе принадлежат игровому каталогу DataRegistry; Studio ссылается на экспортированную версию каталога. Редактирование товаров и выбор единого владельца каталога — отдельный последующий этап, не второй независимый прайс-лист.
5. Снимок: saveSchemaVersion, contentHash, coreVersion, игровое время, seed и состояния RNG, NPCState, счета/запасы/владение, активные действия/дороги/цели, журнал применённых операций. Точный формат денежной единицы, времени и случайности ещё согласовать.
6. Отчёт: runId, версия пакета/ядра, начальные условия, события, контрольные снимки, причины выбора и отказа от действий. Studio импортирует отчёт в отдельный запуск, а не обновляет авторские профили.
7. Один TravelInstance на NPC: видимое движение и дальний расчёт меняют его согласованно; физический актор не создаёт второго владельца местоположения.

## Порядок первого прототипа

A. Согласовать время и сон. При раннем сне обрабатывать весь интервал до следующего утра; day_changed для культур/погоды должен возникать ровно один раз. Отдельно определить поведение на границе полуночи и 02:00, чтобы не смешать календарный день и текущий игровой день.
B. Пакет для Тео, Мартина и Гидеона; загрузчик с проверкой версии и ссылок, без создания полного города.
C. Постоянное состояние и события: work, travel, pay, eat/rest, простое согласованное social action. Тестовые цены и средства помечены как настройки стенда, не утверждённый баланс игры.
D. Небольшой headless-прогон с фиксированным seed и восстановлением из снимка. Разговор доступен только при свободе обоих участников; зарплата имеет реального плательщика, аренда получателя, перевозка источник и груз.
E. Подключить временные акторы к единому состоянию и проверить ближний/дальний режим на S4/S5. Ровенвуд при этом остаётся логическим узлом с местами без окончательных координат.
F. В Studio добавить карту и просмотр отчёта. Прямой запуск Godot кнопкой из браузера требует отдельного решения о локальном мосте/другом способе исполнения; Vercel не объявляется сервером игры.

## Карты и город

Обе карты получены. Сетка 3×3 — концептуальные сектора региона. Подтверждённое пользователем уточнение: показанный город не связан с настоящим Ровенвудом, его планировка и здания не импортируются. Проектирование города — отдельный этап. Жильё, таверна, конюшня и предприятия могут существовать логически до назначения координат. Ферма на схеме — ферма игрока; её нельзя автоматически назначить фермой Мартина.
